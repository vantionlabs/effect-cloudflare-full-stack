# ADR-0022 — API keys are better-auth's, and a key acts as a member

**Status:** accepted · **Date:** 2026-09-30 · **Replaces** an earlier draft of this number that described a
hand-rolled implementation

## Context

`PLAN.md` settled the shape long before the code: _"`X-API-Key` (SHA-256 hashed, shown once) resolves to the
**same** `CurrentUser` as the cookie."_

**It was first built by hand — a table, SHA-256, key generation, issue/list/revoke — and that was a mistake.**
`@better-auth/api-key` exists, is published at **exactly the version of `better-auth` this repo pins** (1.7.6),
and does strictly more. It was missed because it is a separate package: looking in
`better-auth/dist/plugins/` finds nothing, which is very nearly evidence that it does not exist. This repo has a
standing rule against re-cutting auth wheels, and this is what breaking it looks like.

## Decision

**The plugin owns keys.** Generation, hashing, the display prefix, expiry, the `enabled` flag, per-key rate
limiting with quota counters, refill, metadata and permissions are all its. Management is its own routes —
`POST /api/auth/api-key/create`, `GET /api/auth/api-key/list`, `POST /api/auth/api-key/delete` — and the three
`/api/v1/api-keys` endpoints that briefly existed are gone.

**A key acts as a member**, which is the one decision the plugin leaves open and the reason for
`references: "user"`:

Reading the plugin's source settled it. With `references: "organization"` the key's `referenceId` is the
organization and **the creating user is not stored anywhere** — so a verified key yields a tenant and no person.
Our `Identity` needs a `userId`, because `decisions.approved_by` holds one: a decision approved by a program
still has to be attributable to whoever authorised the automation. So a key references its user, and the
organization travels in the key's `metadata`.

**Metadata is a claim, and the membership is the proof.** `metadata.organizationId` is caller-supplied, so on
every request `IdentityForMember` reads `member` and refuses a key naming an organization its user does not
belong to. Two consequences follow, and both are the point: removing somebody from an organization disables
their keys without anything touching a key, and a member's role is the key's role.

## Consequences

- **`AuthenticatedLive` moved to the composition root**, from `packages/api`. It needs a vendor (better-auth
  verifies the key) and a feature (`IdentityForMember` checks the membership), and `dep:check` forbids either
  package from naming the other. The intersection of those two rules is the definition of composition, and the
  check said so the moment the import appeared.
- **`SessionLive` is deleted.** The cookie path is now one branch of one middleware, and better-auth is reduced
  to supplying the `IdentityResolver` port and verifying keys.
- **One declared OpenAPI security scheme, not three.** `HttpApiBuilder` tries schemes in order and falls
  through when a handler fails, and `securityDecode` never fails — so declaring the key and the cookie as
  separate schemes would let a **presented-but-wrong key be retried as a cookie**, which is the exact hole a
  test forbids. One scheme keeps the chain in one handler. The document therefore names `x-api-key` and
  describes `Authorization: Bearer` and the session cookie in prose.
- **The `apikey` table is better-auth's**, generated by `scripts/auth-schema.ts` from the installed library and
  applied as `0023_auth_api_key` — a re-run of the generated file, which is safe only because every statement
  in it is `if not exists`. `auth:check` therefore covers this table too. It is deliberately absent from
  `TENANT_TABLES`: it has no `organization_id`, and no query in this repo touches it.
- **We inherited features we did not ask for**, which is the point of using the library: per-key rate limiting
  closes `.scratch/chat-realtime/issues/08` for the key path, and `permissions` closes the "no scopes" cost the
  hand-rolled version had to admit.

## What this still costs

**A key acting as an owner can mint another key**, because nothing in `Identity` records which door a request
came through. Closing that means a `via: "session" | "key"` on the one type every use case depends on, and
adding a field there without a caller is how a seam accretes. The mitigation is operational: point a key at a
least-privileged member.

**Permissions are available and unused.** The plugin can verify a scope at the same time as the key
(`verifyApiKey({ key, permissions })`), which is the right mechanism for "this key may not approve". Nothing
needs it yet.

## Revisit when

- **A client asks for a read-only key**, or one that may not approve. Then `permissions` stops being unused, and
  the endpoint that must refuse a key gets a scope rather than a new type.
- **Key-minted keys become a concern**, which is when `Identity` gains the door it came through.
- **The plugin moves to organization-owned keys with an actor**, which would make `metadata` unnecessary. Check
  on a better-auth upgrade: this ADR rests on a detail of its source, not on its documentation.
